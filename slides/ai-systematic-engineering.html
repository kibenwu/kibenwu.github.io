01

结构约束

让代码库自己会说话
为什么结构对 AI 比对人更重要

AI 读代码库的方式跟你不一样

人
  • 先看 README
  • 再看架构图
  • 挑一个入口顺着读

—— 自顶向下，有全局

AI
  • grep 一个符号
  • 读几个文件
  • 基于局部样本推断全局模式

—— 检索驱动，靠推断

所以：你的代码库有多一致，AI 推断出的模式就有多准。

我们的约定

目录镜像 · 统一前缀 · 职责域切分

Source/BioExtraction<模块>/
├── Public/<职责域>/BE<类名>.h
├── Private/<职责域>/BE<类名>.cpp   ← 目录结构镜像 Public
└── BioExtraction<模块>.Build.cs

// 跨模块复用同一套一级职责域目录：
Abilities / Animation / Catalog / Components / Debug / Definitions
Effects / Feedback / Instance / Interaction / Loadout / Pickups / Weapons

对人的收益

"整齐"、可读

对 AI 的收益

极大降低上下文熵 —— 结构本身编码了答案

结构一致性的直接回报

"给武器定义加个 Unequip 蒙太奇配置"

结构一致时

AI 不需要问"配置放哪儿"。
Definitions/BEWeaponDefinition.h 里已经有 CharacterEquipMontage，新字段就紧挨着放。

一次找对。

结构混乱时

同样的配置在这个模块叫 Config、那个模块叫 Settings、还有一个硬编码在 .cpp 里。

AI 每次都要重新猜，而且每次猜的结果可能不一样。
这就是 context drift。

推论：结构约定的价值在 AI 协作下被放大了一个量级。
第二条结构原则

配置单点化 —— 把 AI 的盲区收敛掉

// 通用武器表现 actor：由代码从武器定义推入 body mesh / AnimBP（配置单点）。
if (ABEWeaponVisual* WeaponVisual = Cast<ABEWeaponVisual>(NewActor))
{
    WeaponVisual->InitFromDefinition(Cast<UBEWeaponDefinition>(Def));
    WeaponVisual->NotifyAttached(bBuildActive);
    WeaponVisual->ApplyAttachments(Instance->GetAttachments());
}
  • 新增一种武器行为 只需要改一个地方，AI 不需要在 N 个蓝图之间做一致性维护
  • 蓝图恰恰是 AI 读不了的盲区 —— 配置散在蓝图里的系统，AI 命中率断崖式下降
  • 能放代码 / 数据资产的配置，就不要放蓝图
02

知识约束

注释是人机共享的长期记忆
样本 · 全部来自本项目

写"为什么"，不写"是什么"

// 反例（零信息）
// 设置碰撞为无碰撞
Mesh->SetCollisionEnabled(ECollisionEnabled::NoCollision);
// 正例 —— BEMonsterVariantComponent.cpp:477
// 第二个参数 bReinitPose 必须是 false。传 true（SetSkeletalMeshAsset 的默认行为）
// 会走 InitAnim(true)，把 AnimInstance 重初始化、播放时钟归零 ——
// 一波怪同时跨过边界就是一排走路动画倒回第 0 帧。
Body->SetSkeletalMesh(Target, /*bReinitPose=*/false);

标准：没有这条注释，下一个人（或下一轮 AI）一定会踩坑 → 写；否则不写。

为什么这对 AI 尤其关键

这是 AI 唯一能拿到的负面知识

// BEGA_WeaponFire.cpp:344
// 必须走 ApplyGameplayEffectSpecToOwner 而不是 ASC->ApplyGameplayEffectSpecToSelf：
// 后者不带预测键，GAS 对「客户端 + 无预测键 + 非 Instant GE」是直接拒绝的 ——
// 冷却标签在客户端根本没加上，ActivationBlockedTags 形同虚设。
// 从按下到服务器冷却标签复制回来的那一个 RTT 里，能力每帧激活一次 ——
// 一次扣扳机打出好几发、抛好几个壳。
// 单机/监听服务器上因为本地就是权威、GE 立刻生效，所以看不到；
// 只有连独立服务器的客户端会犯。

AI 的训练数据里全是"正确的写法"。

"在我们这个系统里哪些正确写法是错的"
—— 只能靠注释传递。

最后两行直接决定：下一轮 AI 会不会建议"用更简洁的 ApplyGameplayEffectSpecToSelf"。没有这两行，它一定会建议，理由还很正当。
真实事故 · 本项目

反面案例：一条自信的错误注释

bReplicates = true;
// 物理只在服务器模拟（见 StartDropPhysics），客户端完全靠移动复制拿落点。
// 不开这个，掉落会原地悬空不动。
SetReplicateMovement(true);

注释写得斩钉截铁，带因果、带症状描述 —— 完全符合"好注释"的形式。

问题是它是 错的。

AActor::bReplicateMovement 在 AActor 构造函数里的默认值就是 true。这行是空操作。

后果

错误归因被固化进了代码库

有人（或 AI）在"掉落物客户端悬空"这个 bug 上做了错误归因
↓
写了一个没有效果的修复
↓
把错误归因以注释的形式写进代码
↓
bug 一直没修好，但代码里有一段看起来很权威的注释宣称它修好了
任何后续接手的人 —— 包括 AI —— 都会跳过这块

注释是知识资产，也是知识污染源。
AI 会无条件继承代码库里的既有假设。

由此定下的规则

注释规范三条硬要求

  1. 涉及引擎默认行为的结论，必须注明验证方式（引擎版本 + 怎么观察到的），而不只是结论
  2. 网络相关代码必须注明"在哪种环境能复现、哪种环境测不出来"
  3. 设计取舍写在使用现场（属性 tooltip、函数头），不是只写在提交信息里 —— 策划在属性面板上能读到的才算数

一条自信的错误注释，比没有注释危害大得多。

03

验证约束

没跑起来的代码不算完成
案例：武器挂载 notify 重构

需求很清楚

"把 ShowWeapon 这个 notify 的机制修改成为，不是显示武器，
而是在这个消息的时机真正在做 attach 模型的行为，
不需要勾选当前是装备还是不装备，这里自动判定。" —— 需求原文

AI 的第一版实现思路：

if (IsPlayingMontage())
{
    PendingAttachSlots.Add(Key);            // 正在播动画 → 挂起等 notify
}
else
{
    AttachSlotVisual(Slot, V, bActive);     // 没在播 → 当场挂上
}

读起来无懈可击。编译通过。

然后测试反馈来了
"目前编译后测试 发现效果不对啊，
武器是从第一帧就挂在手上了，
而不是等 触发了 notify。"

这句话的结构：实际值 + 预期值 + 精确时间点。
—— 后面 §6 会专门讲，为什么这一句抵得上十句"不生效"。

根因

两条路径的到达顺序没有任何保证

装备状态
属性复制 OnRep_Active / OnRep_Equipped → 何时到达取决于网络
装备动画
GameplayCue → 而且因 LinkAnimClassLayers 重链问题被刻意 SetTimerForNextTick 延后一帧
结果
在"挂起"的那一刻问 IsPlayingMontage() —— 答案几乎永远是 false

这个同步判断 在逻辑上完全正确，在时序上完全无效。

修复：双向兜底

不再问"现在在播吗"，改成"等它起来"

// 不能在这儿直接问"在播蒙太奇吗" —— 装备状态走复制、蒙太奇走 GameplayCue，
// 两条路到达的先后没有保证，挂起的这一刻多半还没开始播，问了永远是否，
// 结果就是枪在第一帧就挂到手上了。改成轮询等它起来。
PendingAttachGraceEnd = World->GetTimeSeconds() + PendingAttachGraceSeconds;
World->GetTimerManager().SetTimer(PendingAttachTimerHandle, this,
    &UBEEquipmentVisualizationComponent::TickPendingAttach, 0.02f, /*bLoop=*/true);
复制先到、动画后到20ms 轮询 0.25s 宽限窗：动画起来交给 notify，一直不起来 → 这把枪没配蒙太奇，当场挂上
notify 先到、复制后到本地预测动画 + 慢一步复制 → 用 LastCommitNotifyTime 时间戳兜住，"该等的那帧刚过"就立即提交
蒙太奇忘了摆 notify动画播完时一次性兜底提交
这个案例说明什么

AI 的默认直觉是"当前帧可观测状态"

它会写 if (当前在播动画)，因为在单机、同步的心智模型里这就是对的。

而分布式系统、异步事件、复制时序 —— 这些地方 "当前帧的可观测状态"根本不是真相。

关键事实

这个 bug 只能通过运行时验证暴露。
编译通过、没有警告、代码审查也看不出问题（逻辑本身是自洽的）。
只有真的跑一遍、看到枪在第一帧就在手上，才能发现。

推论：运行时验证不是"质量保证环节"，而是"信息输入环节"。
人在闭环里提供的不是"批准"，而是 AI 拿不到的那部分事实。

验证闭环断掉的时候

必须明说

Unable to build while Live Coding is active. Exit the editor and game,
or press Ctrl+Alt+F11 if iterating on code in the editor or game
Result: Failed (OtherCompilationError)

改动了头文件（新增成员 / UPROPERTY / 方法 / 枚举值）→ Ctrl+Alt+F11 不够，必须关编辑器。
武器那几轮连续三次改动都涉及头文件 → 连续三轮代码没有被编译过。

硬规则

不要在没有跑过验证命令的情况下说"修好了 / 完成了 / 测试通过了"。
证据先于断言。

这条最容易被违反 —— 因为 AI 输出的最后一段天然倾向于是一个总结，而总结天然倾向于是正面的。
性价比最高的基建

把"能复现问题的最小环境"脚本化

Tools\StartTest_1S4C.bat          // 1 监听服务器 + N 个独立客户端

set "MAP=/Game/Maps/GameLoop/L_Lobby"
set "CLIENTS=2"
start "BE Server" ... "%MAP%?listen" -game -log -port=%PORT%
timeout /t 12 /nobreak >nul
for /L %%i in (1,1,%CLIENTS%) do call :launch_client %%i

如果验证环境不对，一整类 bug 是永远测不出来的。

监听服务器测不出的坑：GAS 预测键去重 · 物理复制 · Cue 本地丢弃 · 复制时序竞态

意义不止"省几次点击"：AI 可以调用脚本，但 AI 没法帮你在编辑器里点十下鼠标。

04

分歧怎么解决

一次完整的排查复盘 —— 掉落物在客户端悬浮
输入：一句话
"在客户端下 spawned pickup 类的物理似乎没有模拟，模型悬浮在空中，
在 listen server 下运行则是正常的。"
层内容作用
现象模型悬浮在空中排除"落点偏了""穿地了"，指向完全没动过
复现条件客户端指向客户端侧
对照组监听服务器正常决定性：服务器物理逻辑没问题，问题在复制链路

这是人能提供而 AI 提供不了的东西 —— AI 跑不了游戏，看不到画面，做不了 A/B 对照。

第一步

收集事实，而不是猜

AI 做的第一件事不是提方案，而是派探索子 agent，只回答事实性问题：

  • pickup actor 的类名和路径
  • 构造函数里 root component 是什么、有没有物理设置
  • 复制相关：bReplicates / bReplicateMovement / GetLifetimeReplicatedProps
  • spawn 调用点在哪、是不是只在服务器执行
  • BeginPlay / OnRep 里有没有按 net role 分支

并且在 prompt 里明确写了："只输出这些，不要提修复方案。"

让 AI 在取证阶段就开始提方案，会导致它为了支撑方案而选择性收集事实。

第二步

枚举假设，逐个排除

假设为什么排除
根组件 Mobility 是 Static那样服务器也会失效，与"监听服务器正常"矛盾
bNetTemporary / DORM_Initial 只有初始复制代码里没设，蓝图不太可能改
网络相关性 / Cull Distance掉落物就在玩家面前
ItemDefinition 对象引用在客户端解析失败那样客户端连模型都看不到，与"模型悬浮"矛盾
客户端物理跑起来但被服务器校正拉住那样落点会接近地面，不会停在出生高度
SetReplicateMovement(true) 没生效这行本来就是空操作 —— 注释是错的（见 §2）
对照组这一个信息，就干掉了表格里第一行和一大类假设。
收敛到的结论

引擎的一次性初始化陷阱

客户端 actor 刚 spawn：Mesh 还没 StaticMesh、还是构造函数设的 NoCollision → 没有刚体
↓
AActor::PostNetReceive() → SyncReplicatedPhysicsSimulation() 恰好在这一刻跑
SetSimulatePhysics(true) 静默失败，且被 bNetCheckedInitialPhysicsState 守着 —— 只跑一次，不重试
↓
服务器一路报 bRepPhysics = true → 客户端一直走物理校正分支
↓
这条分支对"不在模拟的刚体"是空操作，位置分支 PostNetReceiveLocationAndRotation 轮不到
↓
客户端道具永远停在初始复制位置 = 悬空
第三步 —— 我认为整个过程最关键的决策

推理只有 80% 置信度，怎么办？

能解释所有已观察现象，但这台机器上 UE 5.8 只装了二进制，无法读引擎源码逐行确认。

A · 赌假设

按根因做精确小修复 —— 在客户端拿到 mesh 之后手动重新同步一次物理状态。

改动最小。但假设错了 = 白改一轮。

B · 改设计 ✓

落点的正确性不再押在引擎的物理复制通道上 —— 服务器物理停下时，显式复制一份静止变换过来。

让结论不依赖那个假设。

选了 B。

显式复制最终状态

本地物理降级为纯表现

/** 服务器物理停下时的落点（权威）。 */
UPROPERTY(Replicated) FVector_NetQuantize100 RestLocation;
UPROPERTY(Replicated) FRotator RestRotation;

/** 落定标志。放在最后一个复制属性上做通知，保证回调时落点与朝向都已就位。 */
UPROPERTY(ReplicatedUsing=OnRep_RestState) bool bHasRested = false;
void ABESpawnedPickup::OnRep_RestState()
{
    // 客户端本地这一遍落体到此为止，剩下的以服务器落点为准。
    World->GetTimerManager().ClearTimer(PhysicsTimerHandle);
    Mesh->SetSimulatePhysics(false);
    SetActorLocationAndRotation(FVector(RestLocation), RestRotation, /*bSweep=*/false);
}

客户端本地物理起得来 → 落体过程好看；起不来 → 最坏悬 2 秒后被校正到地面，不会永久悬空。

方法论

置信度 → 方案鲁棒等级

  1. 当根因分析置信度不足 100%、且"改设计"成本可接受时，选择让正确性不依赖该假设的方案
  2. 同时埋下能证伪 / 证实原假设的观测点，把这一轮的不确定性转化成下一轮的确定性
BE_INV_LOG(TEXT("[Pickup] StartDropPhysics: %s auth=%d role=%d simulating=%d"),
    *GetNameSafe(this), HasAuthority(), (int32)GetLocalRole(), Mesh->IsSimulatingPhysics());

AI 的根因分析，听起来的置信度永远高于实际置信度。
它会用非常确定的语气讲一个 80% 的结论。
人的职责是给这个结论打折，并据此选择方案的鲁棒性等级。

沟通范式

反过来看 —— 人这边什么样的一句话价值最高
全部来自真实对话原文

很短，但每个字都在缩小搜索空间

动作例句为什么有效
报 bug 带对照组"客户端悬浮，listen server 正常"把范围从"物理系统"缩到"复制链路"
说偏差不说"不对""第一帧就挂手上了，而不是等 notify"实际值+预期值+时间点 → 零次反问定位

明确说不要做什么暂缓清单防止 AI 每轮重新发现同一批问题
展开一条

同一个 bug，三种说法

反馈AI 能做什么
"不生效"只能从头重读全部代码，或反问
"武器挂载有问题"缩到武器挂载模块，但不知道是位置错、时机错还是没挂上
"从第一帧就挂在手上了，
而不是等触发 notify"		立刻定位到"挂起判定失效"这一个点

第三种直接告诉了 AI：挂载逻辑跑通了（否则不会挂上），问题在"延迟提交"那一步。
剩下只需回答一个问题 —— 为什么挂起没生效。

这次从收到反馈到定位根因，中间没有任何一次反问。

压缩比最高的一句

"在武器配置中再增加 Unequip …… 和 equip 一样"

五个字，实际指定了四件事：

  1. 配置字段加在 BEWeaponDefinition.h 里 CharacterEquipMontage 旁边，命名对称
  2. EBEWeaponCueAction 枚举追加 Unequip（且追加在末尾，避免改变既有数值）
  3. 播放路径复用同一个 UGameplayCueNotify_Static，通过 RawMagnitude 传 action
  4. 蒙太奇里复用同一个 Attach Weapon notify

这种压缩之所以成立，前提是代码结构本身足够一致。
如果 equip 的实现是散在三个模块里的特例代码，"和 equip 一样"就什么都没指定。

§1 讲的结构约束，复利在这里兑现。
这个任务的额外收获

对称扩展连带挖出 3 个既有 bug

  1. Cue 解析武器定义的方式是错的 —— 走 GetActiveWeaponDefinition()，对"刚被收起的那把"必然拿不到
  2. PlayEquipCue() 会在手持项没变时误播 —— 往空槽塞装备也会触发一次"拔枪"动画
  3. Server_Unequip 之后缓存变脏 —— 可能驱动一个"模型已销毁的武器"的收起动画，空手比划

这三个 bug 在"只有 Equip"的时候是观察不到的 —— 单向流程恰好绕过了它们。

规律：只实现了单向的系统（只有 A→B 没有 B→A、只有 add 没有 remove），补齐对称路径几乎一定会挖出既有 bug。
这类任务特别适合交给 AI —— 它做对称比较不知疲倦。

AI 这边的两条边界

交还决策权 · 遇阻不绕

案例 · 改 bat 文件

"只需要运行 2 个客户端就行了"

改了 CLIENTS=3→2，没改文件名 StartTest_1S4C.bat，然后主动说明"名不副实了，要改名说一声"。

文件名可能被桌面快捷方式、CI 脚本、肌肉记忆依赖 —— 这些 AI 看不见。

案例 · Live Coding 挡编译

诱惑：换构建目标 / 加跳过参数 / 只编单模块 / 干脆声称"应该没问题"

实际做法：诊断根因（改了头文件，热重载不够用）→ 明确告诉人"关编辑器我编译" → 总结里标注未验证。

遇到阻碍先诊断，不要为绕开阻碍而升级到破坏性操作。

红线：git reset --hard · --force · --no-verify · 删文件
一个小插曲

澄清是有成本的

AI 先弹了一个选择题问。被直接拒绝，然后回了一句：

"先按照XXX来写。"

AI 问一个问题几乎零成本，人回答一个问题要切换上下文。
所以判断标准不是"AI 想不想确认"，而是：

返工代价大

架构选型 · 数据结构 · 外部接口
→ 必须问

返工代价小

命名 · 文案 · 默认值
→ 直接做，并说明假设了什么

行动项 · 已落地

把这一切固化成 AGENTS.md

一页纸总结 · 1/2

AI 的稳定失效模式（重点盯防）

  1. 同步直觉 —— 用"当前帧可观测状态"判断异步/复制时序的事 → 网络代码里几乎必错
  2. 自信的 80% 结论 —— 语气置信度永远高于实际置信度 → 人要打折，据此选方案鲁棒等级
  3. 继承错误假设 —— 无条件相信代码库里既有的注释 → 错误注释比没注释危害大
  4. 顺手多做 —— 不受控的 diff 膨胀 → 用显式"暂缓清单"和边界规则约束
  5. 正面总结倾向 —— 最后一段天然想说"完成了" → 硬规则：没跑过验证不许说修好了
